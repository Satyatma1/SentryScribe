1. Overview & scope

Problem. CCTV cameras record thousands of hours that nobody watches. When something happens, security staff scrub through footage by hand, and incident write-ups are slow and inconsistent.

Solution. SentryScribe processes a video with a pretrained detector (YOLOv8) and tracker (ByteTrack). A rule-based event engine turns the object tracks into timestamped events such as zone intrusion, loitering, crowding and abandoned bags, and writes them to an event log. An LLM then (a) writes a structured incident report from those events and (b) answers natural-language questions about the footage ("When did a truck enter Gate B?") by calling search tools over the event log.

What the system does

  • Accepts uploaded video files (MP4, AVI, MOV, MKV), one clip or a whole folder per run.
  • Detects and tracks people, vehicles and bags frame by frame, with a stable ID for each object.
  • Lets the operator define zones (polygons) and lines on the camera view.
  • Emits six event types with timestamps, keyframe snapshots and confidence values.
  • Generates an incident report (Markdown) that cites event IDs and timestamps, checked by a validator.
  • Answers questions about the footage through search tools, citing the events it used.
  • Runs end to end in one Colab notebook (annotated video, event table, snapshots, report, Q&A), with an interactive showcase page for the results.

Out of scope (deliberately)

  • No model training. Every model is used pretrained, zero-shot.
  • No face recognition or identification of individuals. The system reasons about anonymous track IDs only.
  • No real-time alarm delivery (listed under extensions, §14).

2. Key design decisions

DecisionReason
Pretrained models only There is no time or GPU budget for training. YOLOv8 trained on COCO already covers person, car, truck, bus, motorcycle, bicycle, backpack, handbag and suitcase, which are all the classes we need.
Events come from rules, not ML Rules (geometry + time thresholds) need no training data, are explainable in a viva, and can be tuned per camera from a config file.
The LLM never sees raw video The LLM only receives the structured event log, so every sentence in a report can be traced back to a database row. This keeps hallucinations low and makes the reports auditable.
Tool calling, not LLM-written SQL The query agent can only call a fixed set of typed, parameterised functions. This is safer, and the answers are easier to test.
Open local LLM An open-weights model from Hugging Face runs on the same GPU: no API key, no cost per call, and no data leaves the machine. The citation validator catches the mistakes a small model makes.
Notebook-first delivery The whole pipeline runs in one Colab notebook on a free T4 GPU, so anyone can reproduce it with no local setup. The simulation study executes the notebook's own cells, so the evaluated code is exactly the shipped code.

3. System architecture

The system is organised in five layers. The CV layers (top) run once per video as a background job and produce data. The LLM layer and the application layer (bottom) run on demand and only consume data. The two halves meet only at the event store.

4. Data flow

4.1 Processing a video (offline job)

  1. The operator uploads gate_cam_01.mp4 (or points the notebook at a Drive folder) and checks the zones on a preview of the first frame.
  2. process_video() runs for each clip and prints its progress.
  3. For each sampled frame: detect → track → update per-track state (position history, zone membership, dwell time, last-moved time).
  4. The event engine checks every rule against the updated state. When a condition has held for its minimum duration, an event opens and a snapshot is saved. When the condition stops, the event closes with an end time.
  5. Events, per-track summaries and a run summary are written as JSON, and an annotated MP4 (boxes, IDs, zones) plus event snapshots go to outputs/<clip>/.
  6. The event table, report and question answering then run on those files.

4.2 Answering a question (on demand)

5. Event engine

Every track keeps a small state record. Each rule is a pure function (track_state, scene, t) → condition true/false. A rule that stays true for min_duration opens an event. Hysteresis (the condition must stay false for cooldown seconds before the event closes) prevents a single tracker flicker from creating duplicate events. The object's position is the bottom-centre of its bounding box (its "feet"), which matches ground-plane zones better than the box centre.

Event typeTrigger logicDefault parameters
ZONE_INTRUSIONA person or vehicle's foot point is inside a zone marked restricted.min_duration 1 s
LOITERINGA person stays inside a zone longer than the threshold while moving less than d px overall.dwell 60 s, d = 150 px
CROWDINGThe number of people inside a zone is at or above N.N = 10, min_duration 5 s
LINE_CROSSINGA track's foot point crosses a counting line. The direction comes from the sign of the cross product, and a disallowed direction is flagged as wrong-way.per-line allowed direction
ABANDONED_OBJECTA backpack, handbag or suitcase is stationary with no person within r px.30 s, r = 120 px
VEHICLE_IN_PED_ZONEA car, truck, bus or motorcycle is inside a zone marked pedestrian_only.min_duration 2 s

Handling tracker noise

Real trackers jitter, drop detections, swap IDs and invent short phantom tracks. Six mechanisms keep the rules stable under that noise. Most were added after the simulation study (§11) showed a concrete failure without them, and §11.3 measures each one.

  • Hysteresis. An event closes only after its condition has been false for 2 s, so a missed detection does not split one event into many.
  • ID stitching. When a new ID appears within 1.5 s and 5% of the frame width of a lost same-class track, it continues that track, so loitering timers survive ID switches. The lost track must have lived at least 10 frames, which stops phantom detections from chaining.
  • Position smoothing. Foot points pass through an exponential moving average (α = 0.5) before any geometry test.
  • Line dead-band and debounce. A crossing counts only when the smoothed position is at least 1% of the frame width past the line, the track is at least 3 observations old, and the same track has not crossed in the last 2 s.
  • Bag-attendance gate. A bag is "attended" only by a person track at least 10 frames old, so a phantom person near a bag cannot reset its abandonment timer.
  • Backdated starts. Events carry a since time: an abandoned-bag event starts when the bag was left, not when the 30 s check finally passed.

6. LLM layer

6.1 Report writer

  1. Digest. Events are grouped by type and zone, sorted by time and compressed to a compact JSON list (about 30 tokens per event, so even a long video fits in a single prompt).
  2. Prompt. The system prompt (REPORT_SYSTEM) asks for a fixed structure: Summary · Timeline · Notable incidents · Statistics · Recommended follow-up. It tells the model to use only facts in the digest, to cite every claim as [E<id>], and to say "not observed" rather than guess.
  3. Validate. A post-check extracts every cited ID and timestamp and verifies it against the event log. If a citation is unknown, the report is regenerated once with the error fed back to the model. The final check is stored with the report, so a report that still fails is visibly marked invalid.
  4. Export. The report is saved as report.md next to its validation result (report_check.json).
Illustrative output format (a format example, not a measured result):
"Between 00:02:31 and 00:02:43 a truck entered the restricted Gate B zone [E14]. A second truck entry was recorded at 00:07:05 [E19]. One person loitered near the walkway for 74 s starting 00:11:20 [E22]. No crowding events were observed."

6.2 Query agent tools

ToolPurpose
search_events(type?, object_class?, zone?, t_from?, t_to?, limit=20)Filtered event lookup. This covers most questions.
count_objects(object_class, zone?, t_from?, t_to?)Counts unique tracks, e.g. "how many people used the walkway?"

The agent loop sends the question and tool schemas, executes any <tool_call> blocks it writes, returns the results and repeats (max 6 rounds) until the model produces a final text answer. get_event returns the snapshot path for any cited event.

6.3 Model choice

TaskModelWhy
Incident reports and chat / tool callsQwen/Qwen2.5-14B-Instruct via Hugging Face Transformers, on a Colab A100One model for both tasks. Open weights, about 30 GB in bfloat16 so it fits a 40 GB A100 next to YOLO, and trained for tool calling. Decoding is greedy, so runs are repeatable. Privacy. The LLM runs locally on the same GPU and only ever sees text metadata (event JSON). Nothing is sent to an external service.

11. Evaluation

11.1 Method: simulation study with a held-out test set

The event engine is evaluated on simulated CCTV scenes generated by scripts/simulate.py. Each scene is 120 s at 10 fps on a 1280×720 frame with the default zones, and contains a random mix of scripted behaviours: intruders, line crossers (30% walking the wrong way), a loiterer, a bag drop, a crowd of 10–13 people, a car reversing into the walkway, and 2–6 background pedestrians.

Ground truth comes from a separate labeller that applies the event definitions to the perfect, noise-free trajectories. The engine instead receives the trajectories degraded with tracker-like noise, and its output is scored with the notebook's evaluate() (an event matches when type and zone agree and the start is within ±3 s). The study runs the exact engine code shipped in the Colab notebook.

Protocol. All tuning used 40 development scenes (seed 7). The configuration was then frozen and run once on 100 held-out test scenes (seed 2026, 200 minutes per noise level). 95% confidence intervals come from 2,000 bootstrap resamples of the test scenes. As a reference point, a naive baseline runs the same rules with every noise mechanism of §5 switched off: no cooldown, no stitching, no smoothing, no dead-band, no debounce, no minimum track age and no attendance gate. Reproduce with python scripts/simulate.py. python scripts/build_showcase.py then builds an interactive page (showcase/index.html) with a replay of one test scene.

11.4 Real footage: MOT15 + MOT16

The notebook's benchmark mode (step 3b) runs the full system on all nine static-camera training sequences of the public MOT15 and MOT16 benchmarks: 248 s of video in which every person in every frame is boxed by hand.

  • Zones are placed automatically from where the annotated people walk: a Restricted zone over the least-visited part of the walked area that at least two people enter, a Plaza watch zone over the whole walked area, and an Entry line across its middle. Nobody tunes them by hand.
  • Ground truth is the event definitions applied to the hand-annotated tracks, with no detector or tracker involved. The system has to find the same events from raw video, so the comparison measures what real detection and tracking errors cost.
  • Event types: only people are annotated, so the benchmark covers intrusion, loitering, line crossing and crowding.
  • Short-clip settings: loitering is 10 s, and crowding uses the busiest 10% of each scene's frames, held for 3 s.
  • Matching and output: matching is the same as in §11.1. Step 8 writes precision, recall and F1 overall, per event type and per video to metrics.json.

What the run showed.

  • Occlusion in dense crowds is the hardest case. When people stand still behind each other, the detector cannot see them and the tracker gives them a new ID when they reappear, so a long stay is split. Loitering in crowded scenes is the event type this affects most.
  • The detector size matters on real footage. Small, distant people in busy squares are found more often by YOLOv8x at 1280 px than by YOLOv8s at 640 px, so the notebook uses the larger model on an A100.
  • The incident reports held up. All nine reports from Qwen2.5-14B-Instruct passed the validator, and every cited event ID exists in that video's log. TUD-Campus had no events. Its first draft cited a made-up E0, the validator rejected it, and the retry passed.

Two bugs found during this run were fixed before the final run.

  • Loader bug: the ground-truth loader read a MOT16-only class column in MOT15 files too, where that column holds world coordinates. The loader now reads each benchmark's own layout and stops with an error if a sequence loads no people.
  • Scoring gap: a video with no ground-truth events had its false alarms ignored. Every benchmark video is now scored.

The run's outputs (events, ground truth, scenes, reports and snapshots) are in results/real_footage/.

11.5 Detector and throughput

  • Detector accuracy is not re-measured on COCO, because the models are used as published. Ultralytics reports COCO val mAP50-95 of 37.3 (YOLOv8n), 44.9 (YOLOv8s), 50.2 (YOLOv8m) and 53.9 (YOLOv8x).
  • Colab A100 (YOLOv8x at 1280 px, about 10 frames analysed per second of video): the 248 s of benchmark video took 103 s end to end. Every clip ran faster than real time: 1.6–1.9× for 1080p clips and 2.6–3.6× for smaller ones.
  • Laptop CPU (Intel Core Ultra 9 285H, no GPU, YOLOv8n): ≈7.8 processed frames/s on a 1080×810 test clip sampled at 5 fps, i.e. faster than real time at that sampling rate.

11.6 Limitations

  • The simulated noise model is simplified. Simulated false detections appear at random places, whereas real ones often persist at one spot (a pole read as a person). Occlusion and perspective are not modelled, so the simulation figures describe noise robustness of the event logic, not real-world accuracy.
  • Real-footage ground truth covers people only. Abandoned bags and vehicles are evaluated in simulation only.
  • Real-footage ground truth is the system's own event definitions applied to hand-drawn tracks. It measures detection and tracking errors, not whether the definitions match what a security guard would call an incident.
  • The benchmark clips are short (3–114 s), so the loitering threshold there is 10 s instead of the 60 s used for real CCTV.
  • The query agent is graded automatically against the event log on seven questions. The grading checks that answers are in English, search every video and cite real events of the right type; it does not check counts or wording.

13. Risks & mitigations

RiskMitigation
Tracker ID switches split one person into two tracks, so loitering is missedHysteresis (2 s cooldown) plus ID stitching: a new ID within 1.5 s and 5% of frame width of a lost same-class track continues it. Measured gain: +0.164 F1 at medium noise on the held-out test set (§11.3).
Slow processing on a CPUYOLOv8n at 640 px, sample about 5–10 fps (enough for events that last seconds), and use Colab for long clips.
LLM invents events or timesThe LLM sees only the event digest, must cite every claim, and the validator rejects unknown IDs with one automatic retry.
Small or far objects missed (e.g. bags)A lower class threshold for bags, and YOLOv8x at 1280 px on an A100, which finds more small, distant objects (§11.4). The simulation shows bags are the most noise-sensitive event (§11.2).
People hidden in dense crowdsID stitching joins short gaps, but long occlusions in crowds still split tracks (§11.4). A re-identification tracker is the next step (§14).
A small local model writes a weaker or wrongly cited reportThe validator rejects unknown event IDs and out-of-range times and asks for one rewrite; reports are saved per clip (report.md), so they can be shown without re-running.
Privacy concernsNo identification, anonymous track IDs only, metadata-only LLM calls, and consent for any staged recordings.

14. Extensions

The system is complete as specified. These are natural next steps beyond its scope.

  • Database and dashboard: move the per-clip JSON into SQLite (the schema in §7 maps directly) and wrap the notebook flow in a Streamlit app.
  • Tracking through occlusion: an appearance-based re-identification tracker (e.g. BoT-SORT with ReID) to keep one ID per person in dense crowds, the main cause of missed loitering on real footage.
  • Larger LLM: Qwen2.5-72B-Instruct or similar behind the same generate function, on multiple GPUs or with 4-bit quantisation.
  • Live RTSP mode: the same pipeline on a stream, with events pushed to the UI as they open.
  • Alerts: a Telegram or e-mail notification on ZONE_INTRUSION and ABANDONED_OBJECT.
  • Snapshot captions: a vision-capable LLM describes each event keyframe ("person in a red jacket carrying a box"), with a clear note that the description is model-generated.
  • FastAPI service: REST endpoints (POST /videos, GET /events, POST /reports, POST /chat) so other clients can use the system.
  • Multi-camera: a camera ID on every row and cross-camera questions ("did the truck at Gate B later appear at the dock?").
